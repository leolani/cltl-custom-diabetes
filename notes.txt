They aren't. Nothing in this app puts triples on the event bus. The only event_bus.publish call is in src/myorg/diabetes/service.py:210, and it publishes just the agent's text reply to cltl.topic.text_out. Triples are written straight to the knowledge graph from inside the conversation, with no event in between.

How it flows for each utterance:

1. DiabetesService._process_utterance (service.py:143) calls conversation.respond(text), which ends up in KgChatSession.say() (src/cltl/kg_chat/chat_sessions.py:529).
2. say() calls _annotate_and_push(turn) (chat_sessions.py:682) twice: once for the human's turn (:593) and once for the agent's reply (:623).
3. _annotate_and_push runs the LLM extractor (annotate_new_turn) and then calls _populate_ekg_from_annotations(...) (:738) with kg_address=self.kg_address.
4. That goes to populate_ekg.py. It builds capsules with events_to_capsules.get_capsule_with_event_details_from_turn_with_activity_id and writes them with brain.capsule_event(capsule, ...) (src/cltl/events_from_chat/populate_ekg.py:176). That is a direct call to the triple store through LongTermMemory.

The other write path: _push_gap_triple (chat_sessions.py:896) runs when the human answers a gap or confirmation question. It builds a synthetic annotation and pushes it the same way, through _populate_ekg_from_annotations (:944).

All of this happens synchronously, before the text reply is published. The triples_pushed lists in turn_log are only a simplified view for logging; they are not sent anywhere.

If you want other components to see the triples on the bus, add a publish in _annotate_and_push / _push_gap_triple. Another option is a callback hook like the existing on_new_subject that the service turns into an event.

    def _process(self, event: Event):
        if event.metadata.topic == self._intention_topic:
            self._active_intentions = {intention.label for intention in event.payload.intentions}
            logger.info("Set active intentions to %s", self._active_intentions)
            return

        if event.metadata.topic == self._scenario_topic:
            self._update_chat(event)
            return

        if self._intentions and not (self._active_intentions.intersection(self._intentions)):
            logger.debug("Skipped event outside intention %s, active: %s (%s)",
                         self._intentions, self._active_intentions, event)
            return

        if not self._chat:
            logger.warning("Received utterance outside of a chat (%s)", event)
            return

        if self._dialogue_act_topic:
            self._dialog_aware_processor.process(event)
        else:
            self._process_last_utterance(event.payload.signal)

    def _process_last_utterance(self, text_signal: TextSignal):
        scenario_id = self._emissor_client.get_current_scenario_id()
        self._extractor.analyze_in_context(self._chat)
        response = self._utterance_to_capsules(self._extractor.utterance, text_signal)
        if response:
            self._event_bus.publish(self._output_topic, Event.for_payload(response))
            logger.debug("Published %s triples for signal %s (%s): %s",
                         len(response), text_signal.id, text_signal.text, response)

    def _utterance_to_capsules(self, utterance, signal):
        capsules = []
        for triple in utterance.triples:
            logger.debug("Triple input: %s", triple)
            self._add_uri_to_triple(triple)
            logger.debug("Triple input after adding URI: %s", triple)
            scenario_id = signal.time.container_id

            capsule = {"chat": scenario_id,
                       "turn": signal.id,
                       "author": self._get_author(),
                       "utterance": utterance.transcript,
                       "utterance_type": triple['utterance_type'],
                       "position": "0-" + str(len(utterance.transcript)),
                       ###
                       "subject": triple['subject'],
                       "predicate": triple['predicate'],
                       "object": triple['object'],
                       "perspective": triple["perspective"],
                       ###
                       "context_id": scenario_id,
                       "timestamp": timestamp_now()
                       }

            capsules.append(capsule)
            logger.debug("Capsule input after adding URI: %s", capsule)
        return capsules


Why bigger should help here. The 7B model's weak spots in the test were following the long extraction instructions (about 6k tokens), assigning roles ("felt tired" became a qualifier of the meal), and working out dates. Models in the 30B–120B range are much better at following long instructions and at structured output. The short replies and catch-up questions were already fine at 7B.

Use Qwen for the conversation, not for event extraction. Extraction needs a stronger model: OpenAI, or a bigger local one.

What Qwen3-30B did well today:
- Dialogue: short, natural replies of 1–2 sentences. The catch-up opening, the place question, the intent follow-ups, the one-sentence summaries and the exploration questions all read fine.
- Answers from the knowledge graph: "What do I drink normally?", the "Want the details?" short answers, and the life summary, once the code-fence fix was in.
- Speed: about 1–3 s per reply, 4–14 s per turn that's extracted and stored.
- Cost and privacy: nothing leaves the machine. For health data that's a real advantage.

Where it failed: extraction, which writes the knowledge graph for good

These errors don't stay in one reply. They end up in the timeline and the life summary, and they steer later questions: "What medication did you take?" right after "I didn't take any".

It also needed code workarounds, all now in place:
- a stricter extraction format, because otherwise it returned no activities at all;
- reading JSON out of code fences;
- a cue filter for the recap classifier, which said YES to "At lunch, 1pm" in 10% of tries.

Some of that comes from llama-server's default sampling (temperature about 0.8), which makes yes/no and JSON decisions unstable.

What I couldn't compare. OpenAI had no credits today, so I have no side-by-side run with gpt-5.1. The judgement on OpenAI rests on how the extraction behaved before today, when it ran on gpt-5.1 with tool calls. I didn't measure it today.

Recommendation:
1. Split the backend: extraction on OpenAI, everything else on local Qwen. That's one extra setting (extraction_backend) and a small change; the bulk of the calls, and most of the data, stay local.
2. If everything must stay local:
   - run extraction on a stronger local model, such as gpt-oss-120b, which fits in your 128 GB, or Qwen3-Next-80B;
   - start llama-server with --jinja, so extraction can use real tool calls as with OpenAI;
   - use temperature 0 for the classification and extraction calls.

   I'd test that on a handful of utterances like today's before relying on it.
3. Fix the issues that aren't about the model at all, whichever you choose: catch-up topics mixing people's data, and quit words being ignored.
